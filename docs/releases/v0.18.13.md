# v0.18.13 — the render tools say what they are not for

Benchmarking a website went wrong because `render_html` looks like a page
previewer: it takes HTML, returns a PNG, and a model doing "verify the site"
reached for it instead of running the dev server. The PNG looked like evidence
and proved nothing.

## Changed

- **`render_html`'s description** now states the boundary: it renders one
  isolated document with none of a project's stylesheets, scripts, routes or dev
  server, so it cannot verify a website, an app or a live page — that needs the
  project running in a browser. `render_svg` says the same in one clause.
- **A guard on the result.** When the markup reads like a page — `<script>`
  tags, a linked stylesheet, `nav`/`header`/`main`/`footer`, or asset paths that
  resolve only inside the project — the tool result carries a warning naming
  what was stripped and pointing at the browser route. It stays advisory: a card
  that embeds a local logo still renders.
- **Skills**: `html-to-png` gained a "When NOT to use it" section (stop when the
  warning appears instead of iterating on the PNG); `svg-to-png` gained the same
  one-line limit.
- `docs/rendering.md` states it beside the comparison table.

## Tests

`tests/web-page-guard.spec.ts` — a self-contained card passes; script tags,
linked stylesheets, page landmarks and relative asset paths each flag with their
own reason; the warning text names the dev server and the browser. 413 tests
pass, typecheck and build clean.

## What this does not do

It does not stop a model that ignores the description and the warning — nothing
short of removing the tools does. If a session keeps reaching for them while
working on a site, the blunt fix is still to disable the plugin for that
session; the difference is that now the first misuse is answered in the result
instead of silently producing a misleading picture.
